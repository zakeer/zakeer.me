Scenario Deep-Dives

Frontend → BFF → Backend → Data, for each confirmed scenario. Hotel search is last round's topic and still likely.

Hotel Search Listing Page

Last round's topic — still likely to reappear.

Frontend
  • SSR for initial load (SEO); ISR for city-level pages; CSR for filter/sort after load
  • Stack: Next.js — handles SSR and API routes (BFF) in one
  • State: local filters/sort, React Query for paginated hotel data, Zustand for persisted preferences
  • Components: SearchBar, FilterPanel (dumb), HotelList (smart), HotelCard (dumb), PriceDisplay (dumb)
  • Virtualized list for 100+ results (react-window)
BFF
  • Joins hotel data + availability + pricing + media
  • Handles auth headers, rate limiting, response shaping
  • Returns a paginated, frontend-ready response
Backend
  • Search Service — ElasticSearch for hotel/filter queries
  • Pricing Service — real-time, short TTL cache
  • Availability Service — Redis-backed inventory
Data
  • Hotel metadata — PostgreSQL (stable, relational)
  • Real-time pricing — cache with event invalidation
  • Search index — ElasticSearch
Bring up unprompted"The main risk is real-time pricing causing stale cache. Mitigation: short TTL on price data + optimistic UI with re-validation on hover/focus. The user sees a price immediately; we silently confirm it's current before checkout."
Booking System

The key test: do you understand the double-booking race condition?

Frontend
  • Search results SSR (SEO); ISR for city pages; booking flow CSR (session-critical, form-heavy)
  • React Hook Form for form state; React Query for availability (short TTL); Zustand for booking session (token, step state)
BFF (Next.js API routes)
  • Aggregates availability + pricing + user profile
  • Holds the session token — never exposed to the client
  • Returns a unified BookingContext object; validates auth before hitting downstream services
Backend
  • Availability Service — checks inventory, returns a hold token (10-min TTL)
  • Pricing Service — real-time, short TTL
  • Booking Service — creates reservation, requires an idempotency key
  • Payment Service — separate, called only after booking confirmed
Data
  • Availability holds — Redis, 10-min TTL, prevents double-booking
  • Bookings — PostgreSQL, ACID transactions
  • Pricing — cache, short TTL + event-based invalidation
  • Audit log — append-only, never modified after write
Bring up unprompted"The race condition risk is two users booking the same room simultaneously. Mitigation: optimistic hold in Redis — a 10-minute lock while the user completes payment. Booking commits to PostgreSQL only after payment confirmation. Idempotency keys prevent duplicate submissions on retry."
Payment System

The key test: PCI scope, and why you never build payment processing in-house.

Frontend
  • Never collect raw card data in your own DOM
  • Use hosted payment fields (Stripe Elements, Adyen SDK) — card data goes straight to the provider
  • Optimistic confirmation UI, then verify via webhook — never trust the frontend's success signal
BFF / Backend
  • Create a payment intent on the backend → return client_secret to the frontend
  • Frontend confirms payment with the provider SDK using client_secret
  • Backend receives a webhook on success/failure; booking status updates only on confirmed webhook
Data
  • Payment records — write-only audit log, never deleted or updated
  • Store the provider's transaction ID — never card data
  • Deduplicate webhook deliveries by transaction ID
Bring up unprompted"The frontend never touches sensitive payment data. PCI scope is minimized by hosted fields — our DOM never sees card numbers. Confirmation flow: frontend → provider → provider webhook → our backend. We never trust the frontend's success signal."
Marketing / A-B Testing System

The key test: client-side vs server-side feature flag evaluation, and why it matters.

Frontend
  • Flags evaluated server-side (in the BFF), not client-side — prevents a flash of the wrong variant
  • A/B variant decided at request time, injected into SSR HTML; no switching after hydration
  • Analytics: impression + conversion events fired client-side to an event stream
BFF
  • Receives user context (ID, geo, device, session)
  • Calls the Feature Flag Service, bakes the variant into the page before it reaches the client
Backend
  • Feature Flag Service — segment rules, traffic splits, kill switches
  • Analytics Service — impression + conversion collection
  • Campaign Service — creative assets, targeting, scheduling
Data
  • Flag assignments — Redis, consistent per user per session
  • Analytics events — append-only stream (Kafka → warehouse)
  • Conversion tracking tied to booking ID for revenue attribution
Bring up unprompted"Client-side flag evaluation causes a layout flash. At Agoda's scale I'd evaluate server-side in the BFF so the correct variant is baked into the SSR HTML — that also stops bots from seeing both variants and skewing experiment data."

Deep-Cut Q&A

Crisp, from-memory answers for the topics explicitly named in the HR guide.

When do you use a state manager?

"I use a state manager when I have shared mutable UI state that multiple disconnected components need to read and update — and where that state doesn't come from the server. Shopping cart, preferences, multi-step form state. Server data goes in React Query — that's cache management, not state management. Conflating the two is the most common architecture mistake I see."

Mutable vs. immutable mental models

Valtio — mutable proxy, mutate the object directly and it tracks changes.
Zustand — immutable, return new state via set().
React — immutable by design (reconciler diffs).
Default position: Zustand — aligns with React's mental model, less cognitive mismatch.

HOCs vs. hooks for store connection

"Hooks are ergonomic but subscribe the whole component to the store — if useStore() returns 50 fields and I only care about one, I re-render on every unrelated change. HOCs let me scope the subscription explicitly. For large stores, selector-scoped hooks give the same benefit without HOC complexity."

Context API — when, and when not

Use for low-frequency global state: theme, auth, locale. Don't use for high-frequency state — all consumers re-render on every value change, no batching. Context solves prop-drilling; state managers solve shared mutable state — different problems. Using Redux just to avoid prop-drilling is a common architecture mistake.

Side effects in state managers

Redux-thunk for simple async (single call). Redux-saga for complex flows (cancel, race, orchestration across calls). Zustand — keep side effects outside the store, in a service layer or React Query. Rule: state managers own state, not side effects.

Flux vs. MVC vs. MVVM

"React is fundamentally Flux — unidirectional data flow, single source of truth, view as a function of state. MVC and MVVM are bidirectional by design, which causes synchronization bugs at scale. Flux enforces one entry point per state change. ViewModel classes and two-way binding creeping into React code is a code smell."

Where do you start when designing a component?

"I start with the contract — what data it needs, what events it emits. Then I split: what's stateful (container) vs. what's visual (presentational). I draw that boundary before writing a line. Components that skip this step end up mixing fetch logic with render logic, and they're impossible to test."

PatternWhen to use
Smart vs. DumbSmart owns data/logic; dumb receives props and renders. Enforced boundary = testability + reuse.
Presentational vs. ContainerSame idea, different name. Design team owns presentational; platform team owns containers.
Composition + SlotsWhen a component needs arbitrary structure — expose slots via children or render props. Avoids prop explosion.
Microfrontends — when, and when not
Use when
  • Multiple teams own different parts of one page
  • Independent deploy cycles are needed
  • Tech heterogeneity (React team + Angular team)
Avoid when
  • Shared state across MFEs is required
  • Runtime performance from multiple bundles matters
  • Ops complexity isn't worth the autonomy gained

"I recommend MFEs when team autonomy matters more than runtime performance. For a hotel search page, I'd start with a well-scoped monorepo with domain packages — team ownership without the MFE overhead. MFEs earn their keep when teams genuinely need different release cadences."

CSS-in-JS vs. Tailwind, and design tokens

"CSS-in-JS is great for design-system components needing runtime theming and co-location with logic. Tailwind is better for product feature work — faster iteration, no naming overhead, smaller bundle. At scale, both: Tailwind for page-level feature work, CSS-in-JS or tokens for the shared library."

Design tokens abstract the design decision from the implementation — color.price.highlight instead of a raw hex. One source of truth: design updates the brand without engineers touching component code.
